# Как добавлять контракты, не ломая сохранения

## Кратко

- **Да, в одной локации может быть несколько контрактов.** Они различаются уникальным `contracts.id`, а `location_id` может повторяться.
- Изначально карта содержит четыре места: `0` Сероводье (доска), `1` Топкая низина, `2` Старая мельница, `3` Чёрный бор. Контракты могут находиться в локациях **1, 2, 3**.
- Основной режим PostgreSQL берёт чудовищ и контракты **из таблиц `monsters` и `contracts`** — их НЕ нужно добавлять в `GameService.cpp` или в `src/gui/main.cpp`.
- GUI на Qt 6 группирует доску из `game_.contracts()` по локациям через `QTreeWidget`. Каждый дочерний пункт хранит свой уникальный `contracts.id` в `Qt::UserRole` и передаёт его в `GameService`. Два заказа с одинаковой `location_id` будут двумя независимыми пунктами внутри одной группы и одной точкой на карте.
- После изменения каталога контрактов **перезапустите игру**. Каталог загружается один раз при создании `GameService`.

## Готовый пример: второй заказ на Топкой низине

1. **Не переустанавливайте базу и не очищайте таблицы**. Сделайте резервную копию:

   ```bash
   pg_dump "$BORDERLAND_DB" -f borderland_backup_before_contract.sql
   ```

2. Из корня проекта запустите SQL-файл:

   ```bash
   psql "$BORDERLAND_DB" -v ON_ERROR_STOP=1 -f sql/add_contract_example.sql
   ```

3. Убедитесь, что оба заказа находятся в локации 1:

   ```bash
   psql "$BORDERLAND_DB" -c "SELECT id, title, location_id FROM contracts ORDER BY location_id,id;"
   ```

4. Закройте и снова запустите `./build/borderland_gui` (без `--demo`). В дереве контрактов внутри группы **Топь** появится **«Огни над трясиной»** в дополнение к **«То, что дышит в болоте»**. Оба проходят в Топкой низине.

5. Можно использовать уже существующего героя: при загрузке `PgGameRepository::loadProgress()` выполнит `INSERT ... ON CONFLICT DO NOTHING` и добавит отсутствующие записи `hero_contracts`, не затронув завершённые задания. Примерный SQL-файл тоже выполняет эту операцию. Новые герои получают прогресс по всем контрактам автоматически.

Скрипт можно запустить повторно: записи с теми же ID не будут дублироваться. Он **не перезаписывает** существующий контракт с ID 4 — для изменения текста уже созданного контракта используйте `UPDATE`.

## Свой контракт

Используйте `sql/add_contract_example.sql` как шаблон и замените:

| Поле | Для чего |
|---|---|
| `monsters.id` | Новый уникальный ID чудовища, например `5` |
| `name` | Имя чудовища |
| `max_hp`, `attack`, `defense` | Здоровье, атака и защита противника |
| `weakness` | `fire` (огонь), `silver` (масло), `sigil` (знак ловушки и возможность ритуала) |
| `description` | Описание чудовища при начале боя |
| `contracts.id` | Новый уникальный ID заказа, например `5` |
| `title` | Заголовок в списке заказов |
| `location_id` | `1`, `2` или `3` (можно повторять!) |
| `reward`, `experience` | Золото и опыт за победу |
| `story` | Подробное описание заказа (переносится и прокручивается в GUI) |
| `clue` | Текст, который открывается после расследования |
| `resolution` | Завершение истории после победы или ритуала |
| `monster_id` | Внешний ключ на существующее чудовище |

Не забывайте соответствующий `INSERT INTO hero_contracts ... SELECT ... ON CONFLICT DO NOTHING` для уже созданных героев. Даже без него новая версия автоматически исправит недостающий прогресс при следующей загрузке героя.

**Важно о ритуалах.** В v1.3 мирный ритуал разрешён для чудовищ со слабостью `sigil` (если осталось не более 25 HP и хотя бы 2 единицы сосредоточения). В прежней версии это зависело от жёсткого `contract_id=2`. Для иных разновидностей чудовищ используются обычный бой и знаки.

## Где искать реализацию

- `sql/init.sql` — создание таблиц и начальные три заказа для PostgreSQL.
- `sql/add_contract_example.sql` — пример четвёртого заказа и расширения уже существующих сохранений.
- `src/repository/PgGameRepository.cpp`: `listContracts()` — загрузка всех заказов; `loadProgress()` — автоматически создаёт недостающий прогресс для старых героев.
- `src/service/GameService.cpp`: `acceptContract`, `investigate`, `startBattle`, `turn` — единые игровые правила для любого ID.
- `src/gui/main.cpp`: `refresh()` и `refreshStory()` — отображение дерева заказов и подробностей, выбор по `Qt::UserRole` и ID.
- `src/repository/MemoryGameRepository.cpp` — **отдельный каталог только для режима `--demo` и тестов**. Добавление в PostgreSQL не обновляет демонстрационный режим. Для собственной демо-версии допишите новый `contracts_.emplace_back(...)` там или используйте `addContract()` в тестовом коде.

## Ограничения

- В одном месте может быть несколько заказов, но одновременно возможен **только один активный бой**. После завершения первого можно начать второй, не покидая локацию, если второй заказ расследован.
- Контракты принимаются только в Сероводье (`location_id=0` — доска). Место расследования и боя выбирается через `contracts.location_id`.
- Новый **контракт** в существующей локации требует только SQL. Новая **локация** потребует изменений `locationName()`, проверок ID в `World.cpp` и `GameService.cpp`, карты `MapPanel`, ограничений `CHECK` в базе.
- Не меняйте `contracts.id` у существующих записей: этот ID является частью ключа `hero_contracts` и сохранений.
- Не удаляйте контракты, уже связанные с сохранениями. Если позже понадобится скрывать выполненные/устаревшие заказы, лучше добавить поле `is_active` с миграцией, а не удалять записи.

# Контракты Пограничья — C++17 / Qt 6 / PostgreSQL

Небольшая сюжетная RPG в оригинальном сеттинге мрачного славянского фэнтези. Игрок создаёт охотника, берёт контракты, расследует происшествия, готовит припасы, сражается с чудовищами и развивает навыки.

## Версия 1.4: новый GUI на Qt 6

- FLTK полностью заменена на **Qt 6 Widgets**.
- Адаптивная компоновка: три изменяемые колонки на широком окне и вкладки на узком.
- Обложка и интерактивная карта масштабируются при изменении окна, текст заказов переносится и прокручивается, журнал и действия тоже прокручиваются.
- Доска заказов группирует контракты по локациям, каждый выбирается по **ID**, а не по индексу списка. В одной локации может быть сколько угодно контрактов.
- Существующие данные PostgreSQL **не изменяются** при обновлении с v1.3; не нужно запускать `init.sql` или удалять базу.
- Консольный режим сохраняется. **46 тестов** ядра и модели адаптивного интерфейса, и ещё один smoke-test Qt, если Qt установлена при сборке.
- Инструкции по расширению контрактов: `docs/ADDING_CONTRACTS.md`, `docs/QT_AND_CONTRACTS.md`, `sql/add_contract_example.sql`.

## Возможности

- Несколько персонажей и отдельные сохранения.
- Три оригинальных контракта + неограниченное количество дополнительных в существующих локациях.
- Карта с четырьмя местами: Сероводье, Топь, Мельница, Чёрный бор.
- Расследования (следы или свидетели), бои, знаки, эликсиры, масло, мирный ритуал для духов.
- Торговля, изготовление зелий из трав, отдых за 10 крон, три навыка: меч, живучесть, знаки.
- Сохранение прогресса каждого действия через PostgreSQL одной транзакцией.
- ООП и разделение `domain` / `service` / `repository` / `cli` / `gui`.

## 1. Система и зависимости (WSL / Ubuntu)

Qt 6 запускается в WSL2 при наличии WSLg. Совместимость: Windows 11 или Windows 10 версии 19044 и выше с актуальной WSL; если графический режим отсутствует, см. руководство Microsoft https://learn.microsoft.com/windows/wsl/tutorials/gui-apps.

В **PowerShell** можно проверить:

```powershell
wsl --list --verbose
wsl --update
```

При необходимости перезапустите WSL командой `wsl --shutdown` в PowerShell.

В **Ubuntu WSL**:

```bash
sudo apt update
sudo apt install -y build-essential cmake pkg-config postgresql libpq-dev libpqxx-dev qt6-base-dev
printf 'DISPLAY=%s\nWAYLAND_DISPLAY=%s\n' "$DISPLAY" "$WAYLAND_DISPLAY"
```

Если GUI не открывается, можно установить `x11-apps` и проверить `xeyes`. Для диагностики сборки без дисплея предусмотрен Qt smoke-test в offscreen-режиме.

## 2. Сборка

Рекомендуется создать **новый каталог сборки**, чтобы не смешивать кеш CMake от FLTK с Qt 6:

```bash
cmake -S . -B build-qt -DCMAKE_BUILD_TYPE=Release
cmake --build build-qt -j$(nproc)
ctest --test-dir build-qt -j4 --output-on-failure
```

Если Qt найдена, CMake сообщит `Qt 6 Widgets graphical frontend: ENABLED`. Если не найдена, соберутся CLI и тесты, но `borderland_gui` не появится. Для этого установите `qt6-base-dev`, удалите устаревший кеш сборки либо используйте новый каталог `build-qt`.

Для проверки GUI без физического дисплея:

```bash
QT_QPA_PLATFORM=offscreen ./build-qt/borderland_gui --demo --smoke-test
```

Это проверяет создание окна и смену двух размеров, а не реальное отображение на экране.

## 3. Пробный запуск без базы

```bash
./build-qt/borderland_gui --demo
# либо
./build-qt/borderland_cli --demo
```

В режиме `--demo` данные хранятся **только в памяти** и исчезают при закрытии. Контракты в режиме demo заданы в `src/repository/MemoryGameRepository.cpp`, поэтому новые SQL-контракты здесь не появятся.

## 4. PostgreSQL — постоянные сохранения

Если база у вас **уже есть с версии 1.2 или 1.3**, не пересоздавайте её и не запускайте миграцию повторно: просто задайте переменную подключения и запустите GUI. Перед экспериментами с новыми контрактами сделайте резервную копию.

Для **совершенно новой базы** (выполняется один раз):

```bash
sudo service postgresql start
sudo -u postgres psql -c "CREATE USER borderland_user WITH PASSWORD 'borderland_pass';"
sudo -u postgres createdb -O borderland_user borderland
export BORDERLAND_DB="host=localhost dbname=borderland user=borderland_user password=borderland_pass"
psql "$BORDERLAND_DB" -v ON_ERROR_STOP=1 -f sql/init.sql
```

Если пользователь и БД существуют, пропустите шаги их создания. Это локальные учебные учётные данные — в публичный Git настоящий пароль не добавляйте.

При переходе **с версии 1.1 на 1.4** перед запуском выполните `sql/upgrade_v1_2.sql`, добавляющий поля навыков. С версии 1.2/1.3 миграция не нужна.

Настроить кодировку и запустить обычную игру:

```bash
sudo service postgresql start
export LANG=C.UTF-8
export LC_ALL=C.UTF-8
export PGCLIENTENCODING=UTF8
export BORDERLAND_DB="host=localhost dbname=borderland user=borderland_user password=borderland_pass"
./build-qt/borderland_gui
```

Для консоли: `./build-qt/borderland_cli` (без `--demo`). Успешный запуск подтвердит, что игра видит PostgreSQL; после создания героя прогресс восстанавливается между запусками.

## 5. Добавление второго контракта в одну локацию

Не удаляя старые сохранения:

```bash
pg_dump "$BORDERLAND_DB" -f borderland_backup.sql
psql "$BORDERLAND_DB" -v ON_ERROR_STOP=1 -f sql/add_contract_example.sql
psql "$BORDERLAND_DB" -c "SELECT id,title,location_id FROM contracts ORDER BY location_id,id;"
```

Затем **перезапустите GUI без `--demo`**. На доске внутри Топи появятся два независимых задания: исходное «То, что дышит в болоте» и новое «Огни над трясиной». Старый герой получит новый контракт в состоянии `available` при следующей загрузке: это делает `PgGameRepository::loadProgress()`; завершённые заказы не сбрасываются.

Заказы в одной локации можно принимать и расследовать независимо, но одновременно допускается только один активный бой. Для нового контракта в **существующем месте** достаточно SQL и перезапуска, для совершенно новой локации нужно расширить карту, модель и CHECK-ограничения БД.

## 6. Где что находится

| Каталог | Роль |
| --- | --- |
| `src/domain` | ООП-модель: `Hero`, `Contract`, `Monster`, `Progress` |
| `src/service` | Игровые правила `GameService`, не содержит SQL/Qt |
| `src/repository` | Абстрактный `IGameRepository`, PostgreSQL и реализация в памяти |
| `src/gui` | Qt 6, стили, адаптивные панели и карта |
| `src/cli` | Консольный интерфейс той же игры |
| `src/app` | Фабрика репозитория и выбор режима хранения |
| `sql` | Таблицы, миграция, пример расширения контрактов |
| `tests` | 46 тестов правил, сохранений и политики адаптивной компоновки |

## 7. Ограничения текущей версии

- В базовом мире только четыре точки карты. Добавление **контрактов** в существующее место не требует правки C++; добавление новой **локации** потребует изменений.
- GUI написан на Qt6, но его сборку и реальные окна нужно проверить в WSL с установленной Qt6. В среде подготовки библиотека Qt6 не была доступна. Игровое ядро и CLI собраны, все 46 тестов прошли.
- `QT_QPA_PLATFORM=offscreen` тестирует инициализацию/изменение размеров без настоящего экрана, не заменяет визуальную проверку.
- История Git должна отражать реальные этапы вашей разработки, а не один искусственно созданный финальный коммит.

## 8. Проверка в GitHub Actions

В `.github/workflows/ci.yml` находится CI для Linux: установка Qt6/libpqxx, сборка GUI, 46 тестов ядра и `qt_gui_offscreen_smoke`. Этот workflow запускается на `push` и `pull_request` после публикации репозитория. Реальный запуск GitHub Actions из этой среды не проводился.


## Обозначения заказов на карте (v1.5)

Серо-синий `!` — доступен, золотой `▶` — принят, бирюзовый `?` — расследован, зелёный `✓` — завершён. Цифра показывает число заказов одного статуса на одной локации. Наведи курсор для списка названий, нажми для выбора заказа (повторное нажатие переключает несколько заказов в группе). Подробности в `CHANGELOG_v1_5.md`.

## GitHub Actions: многоэтапный CI

В `.github/workflows/ci.yml` настроены этапы проверки исходников, сборки и 50 тестов CTest, проверки Qt 6 в режиме `offscreen`, интеграционного теста на временном PostgreSQL и упаковки исходников. Этапы Qt и PostgreSQL идут параллельно, финальная упаковка — после их успешного завершения.

Подробные команды Git, описание стадий и работа с артефактами: [`docs/GIT_AND_CI.md`](docs/GIT_AND_CI.md).
